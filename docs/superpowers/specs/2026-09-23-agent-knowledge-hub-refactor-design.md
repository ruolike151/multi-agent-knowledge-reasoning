## 0. 文档目的

本文档定义一个**个人项目**：以参考项目为基线与素材库，重做出一套**真正具备多智能体协作机制、且行为可被量化验证**的企业知识推理系统。

阅读顺序建议：先看 §2（参考项目分析）和 §3（差异化定位）理解「为什么要改造」；再看 §5–§7 理解「系统长什么样」；§9 是本文档最有价值的部分（评测体系），§13 是可执行路径。

本文档是设计规格，不是实现计划。实现计划已由 `writing-plans` 流程产出（Task 1–37，一个任务一个文档），该目录不随本仓库公开；本 spec 只提供「为什么这么做」的依据与章节引用。

## 1. 背景与决策记录

### 1.1 问题

参考项目是一套结构完整、文档详尽的多 Agent 知识管理系统，覆盖编排、多模态解析、知识图谱、增量更新、记忆系统、前后端与容器化。但经代码级审查，其**工程实现与文档宣称严重脱节**：几乎每一个「技术亮点」都是声明式的，缺少可验证的实现与数据支撑（证据见 §2.2）。

直接把该项目的「技术亮点」当成事实的风险是：只需向下追问一层，即可发现其「多 Agent」并非多 Agent、「增量更新」并非增量，且无任何评测数据。此外该项目为他人开源仓库，同类项目已高度同质化。

### 1.2 目标

产出一个**能通过深度技术追问、且能拿出量化数据**的个人项目。判定标准只有三条，反复验证的也只有这三条：

1. 每个技术选型能否说清「为什么这么选、替代方案是什么、如何权衡」
2. 如何证明系统有效（基线、对照、数据）
3. 难点在哪、如何攻克

### 1.3 决策记录

| 编号 | 决策 | 理由 |
|---|---|---|
| D-01 | 采用路线 A：在「企业知识推理」域内重构，而非转向 Deep Research 或纯做评测框架 | 保留参考项目的领域价值与存储选型，参考代码可作素材与基线；「发现开源基线缺陷并量化改进」本身就是加分叙事 |
| D-02 | 参考项目**仅作为只读基线**，不复制其代码进主仓库 | 规避代码来源与「抄袭」叙事风险；保持主仓库全部代码可自主讲解 |
| D-03 | 同时吸收评测框架（路线 C），并把 Deep Research 形态作为一类高难度任务类型纳入评测集 | 三条路线不必互斥；评测体系是最大的稀缺度来源，研究型任务让多 Agent 协作有真实用武之地 |
| D-04 | 模型层统一使用 `deepseek-flash`，以「thinking / non-thinking 双模式」承担全部角色 | 单一模型即可覆盖推理型与格式化两类需求，无需跨模型路由；其价目使多组对照实验在 ¥5 预算内可行，见 §7 |
| D-05 | 多模态解析**保留模型原生视觉理解**，不引入本地 OCR 依赖 | 经官方文档核实，`deepseek-flash` 支持图像输入（JPEG/PNG/GIF/WebP），原「因模型不支持而砍掉视觉」的前提不成立，详见 §7.6 |
| D-06 | API 花费硬上限 ¥5，评测规模据此反推 | 预算直接决定任务集规模与采样次数：核心集 30 题、主表单次采样、12 题子集三次采样，见 §7.7 与 §9.4 |
| D-07 | 语料确定为 A 股上市公司**年报 + 公告**（公开披露文件） | 事实密集、天然多跳、数字可精确验证；公告补充年报不披露的事件型事实（重大合同、对外投资），为多文档综合题提供素材；获取渠道与选取方法见 §8.1 |

> 该目录为 GitHub 仓库 zip 下载（无 `.git`），仅供只读参考。

### 2.1 可复用的部分

| 资产 | 复用方式 |
|---|---|
| 领域选择（企业知识库） | 直接沿用。垂直、业务价值清晰、天然存在多跳关系 |
| 存储选型（向量库 + 图数据库） | 沿用思路，具体选型见 §8.2 |
| 多模态解析的**问题定义** | 沿用「文档格式多样」这一输入约束，实现改为模型原生视觉理解（§7.6） |
| 文档结构（README / 架构说明） | 作为文档完备度的下限参考，我们的文档需更克制、更可验证 |

### 2.2 五个致命缺陷（含证据）

以下每一条都是评审时可能被追问的点，也是本项目要正面解决的问题。

**缺陷 1：「多 Agent」实为固定 DAG，不存在 Agent 协作**

- 证据：`python/orchestrator/graph.py` 中三条流水线的边全部为线性固定连接（`parse → extract → store_vectors → store_graph`），`add_edge` 写死，无动态路由、无任务分解、无协商、无反驳。
- 后果：四个「Agent」之间没有任何交互，本质是四个函数串成的数据流水线。
- 追问风险：必被问「为什么是 4 个 Agent 而不是 1 个带工具的 Agent」，该项目无法回答。

**缺陷 2：「CDC 增量更新快 60 倍」不成立**

- 证据 A：`python/services/cdc_processor.py` 的 `compute_diff` 采用 `set(before_lines) - set(after_lines)` 做行级差量。行集合运算会丢失重复行、无法检测顺序变化、无法定位「第 3 页」。
- 证据 B：`python/agents/knowledge_update_agent.py` 的 `_handle_modify` 实际行为是「按 doc_id 删除该文档全部向量 → 重新解析整个文件」。这正是其 README 所批判的「全量重建」。更新粒度为文档级，而非其宣称的 chunk 级。
- 证据 C：修改路径不清理知识图谱中的旧实体（仅删除路径调用 `delete_by_source`），文档修改会残留陈旧图谱节点。
- 后果：核心差异化卖点不成立。

**缺陷 3：混合检索的分数不可比，「置信度」无意义**

- 证据：`python/agents/qa_agent.py` 中向量分支分数为 `1 - cosine_distance`（连续值），图谱分支为硬编码 `0.8`，随后对二者乘以 1.0 / 1.2 的魔法权重统一排序。两者量纲不同、权重无任何评测依据。
- 证据：`_calc_confidence` 返回上下文的平均分，并非校准概率。
- 后果：检索质量无法度量，也无法调优。

**缺陷 4：无测试、无评测**

- 证据：`python/tests/` 仅含一个 0 字节的 `__init__.py`，无任何测试用例；README 却给出 `pytest tests/` 指引。
- 证据：无检索 recall@k、无抽取 F1、无延迟与成本统计。
- 后果：所有性能主张（如「快 60 倍」）均无数据支撑。

**缺陷 5：健壮性与安全性硬伤**

- 证据 A：`python/services/knowledge_graph.py` 的 `add_relation` 将 LLM 输出的关系类型直接 f-string 拼接进 Cypher 语句，存在注入与语法错误风险。
- 证据 B：`python/agents/qa_agent.py` 的 `_graph_retrieve`、`python/agents/doc_parser_agent.py` 的 `_parse_pdf` 等处大量使用 `except Exception: continue/pass` 静默吞错，故障不可观测。
- 证据 C：`python/api/main.py` 的 lifespan 中 `vector_store.init()` 失败被 `pass` 吞掉，服务会在「检索恒为空」的状态下正常启动，表面可用。
- 证据 D：API 无认证、无鉴权、无限流（README 自述）。

### 2.3 结论

参考项目**适合作为基线与素材库，不适合作为项目本体**。本项目将把它接入为对照实验中的 **Baseline B**，并量化上述缺陷带来的指标差距。

接入方式：作为只读基线目录挂载（Windows 目录联结 junction，脚本 `scripts/mount_baseline.ps1`，绑定到仓库的 `baseline/`，该路径已 gitignore），**不复制其源码进主仓库**。仓库结构见 §11。

## 3. 差异化定位

### 3.1 核心命题

> 把一个「固定流水线式的伪多 Agent 企业知识库」，重做成一个**会规划、会委派、会验证、会诚实拒答的真多 Agent 系统**，并用自建评测集证明它相对单 Agent 基线与固定 DAG 基线的量化收益。

### 3.2 三个必答问题与本项目的答案

| 追问 | 本项目的答案 |
|---|---|
| 为什么需要多 Agent？单 Agent 加工具不行吗？ | 有 Baseline A（单 Agent ReAct）对照数据。收益来自 context 隔离：并行探索 + 独立验证，单 Agent 的 context 会被探索过程污染 |
| 多 Agent 的代价是什么？ | 协调开销与摘要损失。设计目标明确为「最小化协调、最大化隔离」，并在文档中给出 token 与延迟的对照数据 |
| 你怎么知道它变好了？ | 自建任务集（30 条核心集 + 80 条扩展集）、四类任务、成对指标（正确拒答率 / 过度拒答率）、3 组对照、核心集单次采样 + 12 题子集三次采样报方差、judge 与人工一致率校准 |

### 3.3 刻意不做的事

见 §16。**能说出「我为什么不做某功能」和「我为什么做了某功能」同样重要**，这是区分「照着教程搭」与「自己设计」的关键。

## 4. 系统架构总览

### 4.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│  编排层 (Orchestration)                                       │
│  Supervisor 状态机 · 任务账本 · 动态路由 · Verifier 纠错环     │
│  预算熔断 · Context 隔离与压缩                                │
└───────────────┬──────────────────────────────────────────────┘
                │ 原生 Tool Calls + 合法工具集约束
┌───────────────▼──────────────────────────────────────────────┐
│  工具层 (MCP Server，独立进程)                                 │
│  search_documents · walk_graph · resolve_entity               │
│  fetch_chunk · list_documents                                 │
│  约束：不调用 LLM；全部返回溯源元数据                          │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│  数据层 (Storage)                                             │
│  向量库(Chroma) · 图数据库(Neo4j) · 元数据/状态(SQLite)        │
│  Artifact Store：文档原文与 chunk 正文，按 chunk_id 引用       │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  模型层 (DeepSeek · 单一模型 deepseek-flash)                   │
│  thinking 模式：规划 / 路由 / 校验（需多步推理）               │
│  non-thinking 模式：摘要 / 抽取 / 写作（需 JSON 模式）         │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  横切关注点                                                    │
│  Trajectory Logger（全链路 trace）→ 直接喂给评测框架            │
│  Idempotency Store · Checkpointer · 成本与延迟计量              │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 一次问答的完整数据流

```
用户问题
   │
   ▼
[Supervisor] 规划：分解子任务，写入任务账本
   │         判断可答性：语料中是否可能包含答案（否则直接进入拒答分支）
   ▼
[DISPATCHING] 按子任务类型委派：Retriever ×N（并行）/ GraphWalker
   │           每个 worker 只接收自己的子任务描述，context 完全隔离
   ▼
[WORKING] workers 执行 → 各自回传结构化摘要（findings/citations/confidence）
   │        原文不进主 context，只留 chunk_id 引用
   ▼
[VERIFYING] Verifier 逐断言校验：答案中的每条断言是否被其引用原文支持
   │
   ├─ 全部 supported ─────────────────► [SYNTHESIZING]
   ├─ 存在 unsupported 且轮次 < 2 ────► [REVISE] → 带反馈回到 WORKING
   └─ 超轮次 / 超预算 ────────────────► [DEGRADED]（标注不确定，诚实降级）
   │
   ▼
[SYNTHESIZING] 整合为带引用的最终答案
   │
   ▼
输出（答案 + 引用列表 + 执行轨迹）→ 写入 Trajectory，供评测消费
```

## 5. 编排层详细设计

### 5.1 角色划分与存在理由

**设计原则：每个角色的存在理由必须能用一句话说清；说不出理由的角色不应存在。**

| 角色 | 存在理由 | 数量 | 运行模型 |
|---|---|---|---|
| Supervisor | 唯一持有全局视角：任务分解、路由决策、结果整合、可答性判断 | 1 | deepseek-flash · thinking（规划）+ non-thinking（写作） |
| Retriever | 执行混合检索，是「并行探索」的载体 | N（按子任务数并行） | 工具调用不调 LLM；仅回传摘要时用 non-thinking |
| GraphWalker | 多跳关系推理，向量检索无法覆盖 | 1（可并行） | 工具调用不调 LLM；仅回传摘要时用 non-thinking |
| Verifier | 独立校验，防止错误传播；必须与生成方隔离 | 1 | deepseek-flash · thinking |

**明确不设的角色：**

- ReportWriter：写作能力并入 Supervisor。独立写作 Agent 无独立价值，只会增加一次摘要损失与协调开销。
- 独立的 IntentClassifier：意图判断是 Supervisor 规划的自然副产品，单独起一个 Agent 是无效拆分（参考项目的主要问题之一）。

> 该表格即「为什么不搞 10 个 Agent」的完整回答。

### 5.2 状态机与控制流约束

**核心原则：控制流不允许由 LLM 自由决定。** LLM 只能在状态机给定的合法转移集合内做选择。

状态集合：

```
PLANNING · DISPATCHING · WORKING · VERIFYING · REVISE · SYNTHESIZING · REFUSE · DEGRADED · DONE
```

合法转移表（唯一定义处，代码与文档同源）：

| 当前状态 | 合法后继 | 决策者 |
|---|---|---|
| PLANNING | DISPATCHING / SYNTHESIZING（可直接答）/ REFUSE | LLM 在合法集内选 |
| DISPATCHING | WORKING | 确定性 |
| WORKING | WORKING（仍有未完成子任务）/ VERIFYING | 确定性 |
| VERIFYING | SYNTHESIZING / REVISE / DEGRADED | LLM 给判定，转移由规则决定 |
| REVISE | WORKING | 确定性 |
| SYNTHESIZING | DONE | 确定性 |
| REFUSE | DONE | 确定性（输出「无法从知识库确定」，附已检查的范围） |
| DEGRADED | DONE | 确定性 |

实现约束：

- 状态与转移表**显式定义在一处**，Supervisor 的每次决策都先取 `legal_transitions[current]`，模型返回非法状态即驳回并要求重选（最多 2 次，再失败走 DEGRADED）。
- 不用 LangGraph 的隐式 `add_conditional_edges` 承载业务判断（参考项目正是在这里退化成硬编码流水线）。
- 每次转移写入 trace，评测可直接统计「平均步数」「非法转移次数」。

### 5.3 任务账本（Task Ledger）

每个子任务的结构化记录，是 Supervisor context 的主体，也是断点恢复的依据。

```python
@dataclass
class SubTask:
    task_id: str
    goal: str                 # 子任务描述，也是 worker 唯一可见的输入
    kind: Literal["retrieve", "graph", "verify"]
    status: Literal["pending", "running", "done", "failed"]
    depends_on: list[str]
    attempt: int
    result_ref: str | None    # 指向 artifact store 中的结构化摘要，不存正文

@dataclass
class TaskLedger:
    question: str
    answerable: bool
    subtasks: dict[str, SubTask]
    revise_round: int
    budget: BudgetState       # steps / tokens / cost 的已用量与上限
```

### 5.4 Context 隔离与压缩（本项目技术核心）

**这是多 Agent 真正的难点，也是最能体现设计水平的部分。**

隔离规则：

1. Worker 启动时只接收自己的 `SubTask.goal`。**不接收**主对话历史、其他 worker 的上下文、Supervisor 的推理过程。
2. Worker 回传**结构化摘要**，不允许自由文本：

   ```python
   @dataclass
   class WorkerReport:
       findings: list[str]              # 结论性陈述，每条一个断言
       citations: list[Citation]        # 每条断言对应的 chunk_id 列表
       confidence: float                # worker 自评，仅作参考
       open_questions: list[str]        # 未能解决的部分，供 Supervisor 决定是否追加子任务
       cost: CostRecord                 # 该子任务的 token / 耗时，用于成本归因
   ```

3. Supervisor 的 context 组成固定为：**用户原问题 + 任务账本 + 各 worker 的 WorkerReport**。文档原文**绝不进入** Supervisor context，原文存于 artifact store，通过 `chunk_id` 引用。
4. 预算感知压缩：当 Supervisor context 的 token 估算超过阈值时，对**已完成**子任务的 `findings` 做二次压缩，仅保留结论句与 `chunk_id`；`open_questions` 与失败子任务信息不压缩。

**设计洞察：** 多 Agent 的收益来自 context 隔离，成本来自协调开销与摘要损失。因此设计目标是最小化协调次数、最大化隔离程度；凡是无法带来隔离收益的多 Agent 拆分都是负收益。

### 5.5 Verifier 纠错环

| 项 | 设计 |
|---|---|
| 输入 | 候选答案 + **每条断言对应的原文正文**（非检索片段） |
| 隔离要求 | Verifier 看不到生成过程、看不到 Supervisor 的推理，只看断言与原文的对应关系 |
| 输出 | 逐断言判定 `supported` / `partially_supported` / `unsupported` + 判定理由 |
| 触发回退 | 存在 `unsupported` 且 `revise_round < 2` |
| 反馈注入 | Verifier 的理由作为 REVISE 的反馈，注入下一个 WORKING 轮次 |
| 兜底 | 超轮次或超预算 → DEGRADED：输出已知部分并显式标注不确定项，**不硬编** |

### 5.6 预算熔断

全局预算，任一触顶即强制收敛到 SYNTHESIZING 或 DEGRADED：

```python
@dataclass
class Budget:
    max_steps: int = 24        # 状态转移步数
    max_llm_calls: int = 40
    max_tokens: int = 120_000
    max_cost_cny: float = 0.5
    max_wall_seconds: int = 120
```

替换参考项目中「最多重试 3 次」这类无依据的常数——重试上限应由预算驱动，而非拍一个数字。

## 6. 工具层（MCP）详细设计

### 6.1 工具清单与契约

设计原则：**面向意图，不是给已有 API 套壳。**

```python
search_documents(query: str, top_k: int = 8,
                 doc_filters: dict | None = None) -> SearchResult
# SearchResult: { hits: [Hit], fusion: "rrf", retriever_stats: {...} }
# Hit: { chunk_id, doc_id, source, text, score, retriever: "vector"|"bm25"|"both" }

walk_graph(entity: str, hops: int = 2,
           relation_types: list[str] | None = None) -> GraphResult
# GraphResult: { paths: [{ nodes: [EntityRef], relations: [RelRef], text: str }] }

resolve_entity(mention: str, context: str = "") -> EntityResult
# EntityResult: { candidates: [{ entity_id, name, type, aliases, score }] }

fetch_chunk(chunk_id: str) -> ChunkResult
# ChunkResult: { chunk_id, doc_id, source, text, char_range }

list_documents() -> DocumentOverview
# DocumentOverview: { documents: [{ doc_id, source, doc_type, chunk_count, updated_at }] }
```

### 6.2 三条硬约束

1. **检索类工具不调用 LLM。** 保持纯函数、可单测、可 mock。常见追问是「工具里能不能调模型」——答案是不能，否则不可测、不可替换模型、成本不可归因。
2. **所有返回值携带溯源元数据**（`source` / `chunk_id` / `score`）。没有溯源，§9 的引用支撑率无法自动计算。
3. **独立为 MCP server 进程**，Agent 通过 MCP client 调用。工具层与编排层解耦，同一套工具可被任何 agent 框架复用——这是 MCP 的真正价值，也是这套架构最实的工程收益。

### 6.3 检索融合：RRF

替换参考项目中「分数乘权重再相加」的错误做法。

向量相似度（连续值）与 BM25 分数（无上界）量纲不同，直接加权相加在数学上不成立。改用 **RRF（Reciprocal Rank Fusion）**：

```
score(d) = Σ_over_retrievers  1 / (k + rank_i(d))        # k 通常取 60
```

RRF 只依赖排名、不依赖分数尺度，天然免归一化，且对单路召回质量差异鲁棒。

**设计价值：** 明确指出「参考实现把不同量纲的分数加权相加」的问题，并给出 RRF 这一标准解法。

### 6.4 MCP server 形态

- 传输方式：stdio（本地开发）或 streamable HTTP（演示）
- 工具以 MCP tool schema 声明，包含输入/输出 JSON Schema
- Agent 侧通过 MCP client 动态发现工具，而非硬编码函数名——这样「工具集变化」不会导致编排层改动
- 附加收益：MCP server 可独立单测，并在评测中作为组件级指标（工具调用成功率）的观测点

## 7. 模型层设计（DeepSeek · deepseek-flash）

> 本节能力与价格均按 2026-09-23 查阅的 DeepSeek 官方文档（Models & Pricing / Thinking Mode / Tool Calls / Context Caching / Vision）记录。官方价格与能力会调整，实现时以当期文档复核。

### 7.1 能力边界及其对架构的约束

| 能力 | 状况 | 对设计的约束 |
|---|---|---|
| 模型 | `deepseek-flash`（DeepSeek-V4.1-Flash），`base_url = https://api.deepseek.com` | 全项目单一模型，**无跨模型路由**；旧名 `deepseek-v4-flash` 仍被接受但已退役，代码与文档统一写 `deepseek-flash` |
| 上下文长度 | 1M | **约束放松**：不再需要为「塞不下」而激进裁剪。但 context 隔离仍必须做——隔离的目的是抗污染与省成本，不是为了不超窗 |
| thinking 模式 | 默认开启（默认识力 high），可关闭：`{"thinking":{"type":"enabled"/"disabled"}}` + `reasoning_effort` | 路由单位从「模型」变为「模式」（§7.2） |
| 结构化输出 | 支持 JSON Output | **不保证符合 schema**，仍需自建校验 + 自修复层（§7.4） |
| Tool Calls | 支持，thinking 与非 thinking 模式均可 | 直接用原生 tool calls，但工具集合由状态机限制（§7.3） |
| 视觉输入 | 支持（JPEG/PNG/GIF/WebP；请求体上限 48 MiB） | 多模态走模型原生视觉，不引入本地 OCR（§7.6） |
| 前缀缓存 | 自动缓存；命中价约为未命中的 1/50 | prompt 前缀稳定化是高收益优化，且可被精确计量（§7.5） |
| 并发上限 | 2500（flash） | 并行 worker 不受并发约束 |

**thinking 模式必须处理的三个坑：**

1. thinking 模式下 `temperature` / `presence_penalty` / `frequency_penalty` **不生效**（不报错但被忽略），`top_p` 有效区间被压到 0.95–1.0，非 thinking 模式固定为 1.0。不要写依赖 `temperature` 调参的逻辑。
2. 思维链经 `reasoning_content` 返回，且**同样计入输出 token 计费**——thinking 调用成本显著高于 non-thinking，预算模型必须区分（§7.7）。
3. **请求带 `tools` 时，历史轮次的 `reasoning_content` 必须回传**；不带 `tools` 时无需回传。这条直接决定 §7.3 工具循环的实现方式。

### 7.2 单模型双模式路由

| 用途 | 模式 | 理由 |
|---|---|---|
| 任务规划、路由决策、可答性判断 | thinking（effort=high） | 需要多步推理，质量优先 |
| Verifier 逐断言判定 | thinking（effort=high） | 判定质量直接决定纠错环有效性 |
| Worker 结果摘要、结构化抽取 | non-thinking | 需要 JSON 输出与低延迟 |
| 最终答案综合写作 | non-thinking | 模板化程度高，速度优先 |
| 评测 judge（答案正确性） | thinking（effort=low） | 需要推理能力，但可降 effort 控成本 |
| 评测 judge（引用蕴含判断） | non-thinking | 调用量大，成本敏感 |

**模式路由本身就是一项值得单独度量的优化**，可在评测中独立对照（「全部 thinking」与「按表路由」：质量差 vs 成本差）。

### 7.3 原生 Tool Calls + 合法工具集约束

`deepseek-flash` 原生支持 Tool Calls（thinking 与非 thinking 模式均可），因此本项目不绕开原生机制，而是在其上加约束：

1. 状态机根据当前状态产出**合法工具集合**（WORKING 状态下仅允许 `search_documents` / `walk_graph` / `resolve_entity`）
2. 仅把该集合的 schema 作为 `tools` 参数传给模型，模型原生返回 `tool_calls`
3. 校验工具名与参数是否满足各自 JSON Schema；非法则把校验错误回灌要求重选（最多 2 次，再失败抛结构化异常，由编排层降级）
4. **工具的构造与执行始终由代码完成**，模型只做选择

**控制流仍不由 LLM 决定**：模型在合法集合内选工具，但「下一步进入哪个状态」由转移表决定（§5.2）。

**实现要点（来自官方文档）：** 工具循环中历史 assistant 消息需完整回传（含 `reasoning_content`），`tool` 角色消息必须带对应的 `tool_call_id`。

### 7.4 结构化输出：校验 + 自修复

JSON Output 只保证「输出是合法 JSON」，**不保证符合我们的 schema**，因此实现统一解析层：

```
parse_with_repair(raw, schema, max_repair=2):
    1. 剥离代码块围栏 / 前后缀噪声
    2. json.loads
    3. pydantic schema 校验
    4. 失败 -> 将「原始输出 + 校验错误信息」回灌给模型要求修复，重试
    5. 超过 max_repair -> 抛出 StructuredOutputError，由调用方决定降级（不可静默返回空对象）
```

**必须与参考项目的行为形成对照：** 参考项目解析失败即返回空结果（`return ExtractionResult(entities=[], ...)`），导致错误静默传播（§2.2 缺陷 5）。我们的版本要么修复、要么显式失败。

### 7.5 前缀缓存与成本优化

官方缓存机制以**完整匹配的 cache prefix unit** 为准，命中部分按缓存价计费（约为未命中价的 1/50），并在 usage 中返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，可直接计量。因此：

- 所有 prompt 采用 **「稳定前缀 + 动态后缀」** 结构：system prompt、输出 schema 说明、few-shot 示例全部前置且逐字固定；用户问题、检索结果等动态内容一律后置
- 禁止在 system prompt 中插入时间戳、随机 id 等易变内容
- 每条 trace 记录 cache hit / miss 的 token 量，直接量化该优化带来的成本下降
- 缓存是 best-effort 且数小时至数天后清除，因此**同一批实验应连续跑完**，不要跨天拆散，否则命中率显著下降

### 7.6 多模态：使用模型原生视觉（修订 D-05）

经官方文档核实 `deepseek-flash` 支持图像输入，因此原 D-05 的前提不成立，改为：

- 图片与扫描件：直接以 `image_url` 内容块送入模型做视觉理解（本地文件用 base64 `data:` URL；重复使用的图用 Files API 拿 `file_id` 复用）
- PDF 文字：`pdfplumber` / `PyPDF2` 提取
- 表格：`pdfplumber.extract_tables` 或 `openpyxl` 转结构化文本
- **不引入 PaddleOCR / Tesseract**：模型已具备视觉能力时，本地 OCR 只是多一个重依赖和一处不可独立评测的失败点（YAGNI）

> 修订说明：原 D-05 以「DeepSeek API 不支持图像输入」为前提，该前提经 2026-09-23 官方文档核实不成立。
>
> 多模态仍排在里程碑后段（M5 之后）处理，主线先做纯文本，避免成为时间黑洞。

| Checkpoint | **自研 SQLite 检查点表**（序列化任务账本） | 替代 LangGraph checkpointer：转移表已显式定义，自研检查点依赖更少、更易单测 |

### 8.3 增量更新（真正做对）

参考项目的增量更新是文档级全量重建。本项目的正确实现：

1. **Chunk 级指纹**：每个 chunk 存 `content_hash`
2. **文档结构树**：解析时保留章节层级，修改后先做结构对齐，再逐节点比对 hash
3. **差量集合**：得出 `added_chunks` / `removed_chunks` / `unchanged_chunks`
4. **增量写入**：仅对 added 做向量化与图谱抽取；removed 从向量库与图谱中精确删除（含其独占的实体与关系）
5. **实体引用计数**：图谱节点记录来源 chunk 集合，避免删除某文档时误删仍被其他文档引用的实体
6. **量化**：报告「修改一份文档中 1 页」时，重新向量化的 chunk 数与耗时，与文档级全量重建对照

> **已确认全做**（见 §17 Q-04）：6 项全部纳入范围。其中第 2 项（文档结构树）与第 5 项（实体引用计数）是「做深一个点」的核心卖点，也是相对参考项目最直接的对照证据。

## 9. 评测体系设计（本项目最大差异化）

### 9.1 任务集构造

受 ¥5 预算约束（§7.7），任务集分两档：**核心集 30 条**（必跑，进入主对照表）与**扩展集 80 条**（预算外，按需追加）。

核心集 30 条，四类：

| 类型 | 数量 | 考察点 |
|---|---|---|
| 单跳事实 | 8 | 基础检索能力 |
| 多跳推理 | 10 | 图谱 + 跨文档连接能力 |
| 多文档综合 | 7 | 汇总对比、研究型任务能力 |
| 应拒答 | 5 | 诚实度：知识库不存在答案时是否明确说不知道 |

扩展集在核心集基础上扩到 80 条，比例保持相近（单跳 20 / 多跳 28 / 多文档综合 18 / 应拒答 14）。**任务集格式从第一天就按 80 条设计**，扩集只是加数据，不改代码。

**构造方法（反向构造，避免「自己出题自己答」的无说服力做法）：**

1. 从语料中提取事实三元组与关键数字
2. 由模型生成候选问题 + gold 答案 + **精确到 `chunk_id` 的 gold 引用**
3. 人工复核全部 gold 引用，并抽检 ≥30% 的题目质量
4. 应拒答类构造手法：实体替换（询问语料中不存在的公司的高管）、时间错位（询问尚未发生的事件）、关系不存在（询问两个真实实体间不存在的关联）

任务记录格式：

```json
{
  "task_id": "multi_hop-007",
  "type": "multi_hop",
  "difficulty": "hard",
  "question": "...",
  "gold_answer": "...",
  "gold_chunk_ids": ["doc3#chunk-12", "doc7#chunk-04"],
  "answerable": true,
  "notes": "需要跨两份文档连接子公司与业务线"
}
```

### 9.2 指标定义

**组件级：**

| 指标 | 定义 |
|---|---|
| 检索 recall@k | gold_chunk_ids 中被召回的占比 |
| 检索 MRR | 首个相关 chunk 的排名倒数均值 |
| 工具调用成功率 | 工具调用返回有效结果的比例 |
| 实体链接准确率 | `resolve_entity` 首选候选正确的比例 |

**任务级：**

| 指标 | 定义 |
|---|---|
| 答案正确率 | LLM-as-judge 按 rubric 打分（含人工抽检校准） |
| **引用支撑率** | 答案拆为原子断言后，被其引用原文蕴含的断言占比 |
| 幻觉率 | 无任何引用支撑的断言占比（= 1 − 引用支撑率） |
| **正确拒答率** | 应拒答集合中正确回答「无法从知识库确定」的比例 |
| **过度拒答率** | 可答集合中被错误拒答的比例 |

> **正确拒答率与过度拒答率必须成对报告。** 只报前者，系统可以通过「一律拒答」刷分；成对报告才是真实的诚实度度量。这一对指标的设计本身就是评测设计的要点。

**系统级：**

| 指标 | 定义 |
|---|---|
| 端到端延迟 | P50 / P95 |
| 每任务成本 | token 与人民币，区分缓存命中/未命中，按模型归因 |
| 平均状态转移步数 | 编排效率 |
| 非法转移次数 | 状态机约束的实际有效性 |
| 故障恢复率 | 注入故障后成功恢复并完成任务的占比 |

### 9.3 对照实验设计

**同一套语料、同一套工具、同一套模型、同一套任务集，仅编排策略不同：**

| 组 | 编排方式 | 角色 |
|---|---|---|
| Baseline A | 单 Agent ReAct（全工具，循环调用） | 回答「单 Agent 加工具不够用吗」 |
| Baseline B | 固定 DAG（参考项目原样运行，路径见 §2） | 回答「固定流水线差在哪」 |
| Ours C | Supervisor 动态路由 + 并行 Worker + Verifier 纠错环 | 本项目 |

产出物为一张覆盖全部指标的对照表——这是本项目最核心的产出。

### 9.4 统计严谨性（受预算约束的采样策略）

LLM 输出有随机性，单次运行的结果不具说服力；但 ¥5 预算无法支撑「全量 × 3 次采样」。因此采用**分层采样**，并把这一取舍明确写进报告：

| 范围 | 采样次数 | 用途 |
|---|---|---|
| 核心集 30 题 × 3 组 | 1 次 | 主对照表（给出点估计） |
| 核心集中抽 12 题 × 3 组 | 3 次 | 方差与稳定性估计（给出均值 ± 标准差） |
| judge 校准集 15 题 | 1 次 + 人工 | judge 一致率与 Cohen's κ |

其余要求：

- 主表的置信区间由 12 题子集的方差外推，并**在报告中注明该外推假设**，不假装是 30 题的实际方差
- 关键结论（如「成功率提升 X%」）必须同时给出子集上的波动范围
- 三组实验在**同一天、同一模型版本**下完成，避免模型静默更新导致的漂移

### 9.5 judge 可靠性校准

LLM-as-judge 若不加校准，其结论可信度低：

1. 从核心集 30 题中人工标注 15 题作为校准集（**人工标注的判据是 gold 答案与 gold 引用，不参考系统输出**）
2. 计算 judge 与人工判定的一致率（并报告 Cohen's κ）
3. 若一致率不足，调整 rubric，或对分歧样本引入多 judge 投票
4. **在校准集上的一致性数据需写入文档**——这是绝大多数同类项目完全缺失的部分

| 项 | 设计 |
|---|---|

| 健康检查 | 启动时依赖不可用应**快速失败**，而非带病启动（对照参考项目的 `except: pass`） |

## 14. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 语料准备成为时间黑洞 | 阻塞 M1/M2 | M0 冒烟不等语料：用任意 `.txt` / `.md` 文档验证基线链路；正式语料（10 份年报 + 5 份公告）先跑通全链路，验证后再扩充；语料选择（公司与年份名单）已在 M0 定死，见 §8.1 |
| 任务集质量不足（自出题自答） | 评测结论不可信 | 反向构造 + gold 引用人工全量复核 + 抽检 30%；报告 judge 与人工一致率 |
| DeepSeek 结构化输出不合 schema | 解析失败率升高 | §7.4 的校验与自修复；失败必须显式报错，禁止静默降级 |
| thinking 模式参数不生效导致调参白费 | 调试时间浪费 | §7.1 已记录：thinking 下 `temperature` 等参数被忽略，`top_p` 被压到 0.95–1.0；不写依赖这些参数的逻辑 |
| **API 预算超支** | 实验中断、结论不完整 | 按 §7.7 分配预算；每题设调用与成本熔断；批量实验安排在**夜间或周末**（价格减半）；开发联调一律用 mock 单测与 5 题 smoke |
| 预算不足导致统计强度偏弱 | 结论说服力下降 | §9.4 分层采样并显式标注外推假设；需要更强结论时按 §17 Q-05 追加预算 |
| 多 Agent 摘要损失导致质量下降 | 目标架构不如单 Agent | 这正是要度量的现象。若数据不支持多 Agent 更优，则如实报告并分析适用边界——**诚实的负结果也是可讲的技术结论** |
| 多模态解析耗时 | 拖延主线 | 视觉通道排到 M5 之后；主线只处理文本类文档 |
| 自研状态机的边界情况遗漏 | 非法转移处理不完整 | 转移表**单点定义**，并用表驱动测试穷举全部「状态 × 目标」组合，非法组合必须被拒绝 |

## 16. 明确不做的事（YAGNI）

| 不做 | 理由 |
|---|---|
| 不复制参考项目源码 | 规避来源与抄袭叙事风险，保持全部代码可自主讲解 |
